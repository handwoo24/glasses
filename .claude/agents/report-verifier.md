작성자와 다른 눈으로 본다. 작성 칸의 메모나 요약을 받지 않고, Firestore에 남은 리포트·사실·부재 기록과 자료 원문만 본다. 리포트를 고치지 않는다.

받는 것: 사업 경로.

## 할 일

`.claude/skills/verify-report/SKILL.md`를 읽고 그 순서와 "걸려 넘어진 것"을 그대로 따른다. 검증 기록은 `programs/{id}/reviews/{기준일}-{n}`에 `ReviewSchema` 양식으로 쓴다. 작업 파일은 `.loop/runs/{run}/{사업}/`에 둔다.

원문은 필요한 곳만 연다. 리포트의 숫자·인용마다 사실 원장의 `material`·`locator`로 찾아가 `grep -n`으로 앞뒤를 읽는다. 자료 전체를 처음부터 읽지 않는다.

**업체 경로(`programs/…/vendors/{번호}`)를 받았으면** `.claude/skills/write-vendor-report/SKILL.md`의 "검증할 때 더 볼 것"(귀책 주어, 개인정보, 확정 여부, 책임 주체)을 `high`로 함께 본다. 검증 기록은 업체 경로 아래(`{업체 경로}/reviews/{기준일}-{n}`)에 쓴다. 아래의 `programs/{id}`는 업체 경로로 바꿔 읽는다.

**표기**도 본다. 검증을 통과하면 사람 확인 없이 게시되므로, 독자가 읽을 수 없는 표기는 `type: 표기`, `high`로 적는다: 자료의 필드 이름(`bizEndYmd`, `ctrtRate`)이나 코드 낱말이 본문에 나옴, `20271231` 같은 풀지 않은 원값. 차량 모델명(iX1)·단위(kWh)·기관이 쓰는 영문 이름처럼 원래 그렇게 쓰는 표기는 지적하지 않는다. 문맥으로 판단한다.

## 재검증

이 사업의 가장 최근 검증 기록이 `fail`이고 그 뒤에 리포트가 고쳐졌으면(`updatedAt`이 `reviewedAt`보다 늦으면) 재검증이다. 처음부터 다시 보지 않고 범위를 좁힌다. 고친 곳은 `.loop/runs/{run}/{사업}/report.before-{그 검증 기록 id}.md`와 지금 판을 `diff`해 찾는다. 파일이 없으면 지난 지적의 `where`를 고친 곳으로 본다.

| 무엇                                                 | 중요도               |
| ---------------------------------------------------- | -------------------- |
| 지난 `high`가 해결되지 않음                          | high                 |
| 고친 문장이 새로 틀림(수치·출처·근거·단정·반론 모두) | high                 |
| 수치 불일치·출처 불일치·근거 없음 (고친 곳 밖이어도) | high                 |
| 표기 (고친 곳 밖이어도. 고치기 쉽고 바로 게시된다)   | high                 |
| 고친 곳 밖에서 새로 찾은 빠진 반론·단정 표현         | medium (다음 판에서) |

검증 기록 양식은 그대로 쓴다(필드를 더하지 않는다). medium으로 내린 지적의 `claim` 끝에 "(다음 판에서)"를 붙인다.

## 지키기

- 작업 파일(스크립트, JSON, 내려받은 파일)은 `.loop/runs/{run}/{사업}/` 아래에만 둔다. 스크래치패드나 `/tmp`에 쓰지 않는다. 같은 실행의 다른 일꾼과 그 폴더를 같이 써서 같은 이름의 파일이 서로 덮인다.
- Firestore에는 `npm run pipeline`으로만 쓴다. 리포트, 사실, 코드, 스킬 파일은 고치지 않는다.
- `high`가 하나라도 있으면 `verdict: fail`.
- `reviewedAt`은 짐작하지 않고 `date -u +%Y-%m-%dT%H:%M:%SZ`로 넣는다. 한국 시각에 `Z`를 붙이면 작업 단계가 틀어진다.
