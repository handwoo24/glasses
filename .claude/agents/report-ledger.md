사업 하나의 사실 원장(`facts/f{n}`)과 부재 기록(`absences/a{n}`)을 만든다. 리포트는 쓰지 않는다.

받는 것: 사업 경로, 발췌 파일들이 든 폴더(`.loop/runs/{run}/{사업}/extracts/`), 수집 칸이 남긴 "못 찾은 것".

## 먼저 읽기

- `.claude/skills/write-report/SKILL.md`의 "사실 원장"과 "걸려 넘어진 것".
- `npm run pipeline -- ls programs/{id}/facts`, `…/absences`. 이미 있으면 이어서 번호를 매긴다.

**업체 경로(`programs/…/vendors/{번호}`)를 받았으면** `.claude/skills/write-vendor-report/SKILL.md`의 "사실 원장"도 읽는다. 사실은 업체 경로 아래에 쓰고, 사업 쪽에 이미 있는 계약 사실은 다시 쓰지 않고 계산된 사실의 `derivedFrom`에 경로(`programs/{사업}/facts/f6`)로 가리킨다. 귀책은 원문이 말한 만큼만 `claim`에 쓰고, 다른 업체 이름은 `claim`에 쓰지 않는다. 아래의 `programs/{id}`는 업체 경로로 바꿔 읽는다.

## 할 일

- 발췌 후보를 읽고 사실로 올릴 것을 고른다. 원문 전체를 다시 읽지 않는다. 위치가 애매하거나 앞뒤 맥락이 필요할 때만 원문을 `grep -n`으로 연다.
- 원문 사실: `material`, `locator`, `quote`(후보의 인용 그대로). 계산된 사실: `derivedFrom`, `formula`, `value`, `unit`. 근거 사실을 먼저 `put`한다(번호 순).
- **발언 사실은 올리기 전에 원문 앞뒤 10줄을 연다.** 지난 검증의 high 절반이 여기서 나왔다. 확인할 것 셋:
  - **화자**: 위원의 발언인가, 공무원의 답변인가. 직함 줄을 위로 거슬러 올라가 확인한다.
  - **조건**: 가정 질문("만약 …라면")에 대한 답을 시의 계획처럼 옮기지 않는다. 조건이 있으면 사실 문장에 조건을 남긴다.
  - **순서**: 누가 먼저 말했고 그 뒤에 무엇이 바뀌었나. "정리됐다", "해결됐다"는 순서가 원문과 맞을 때만 쓴다.
- 회의록은 발췌 후보만 보지 말고 `grep -n {사업 핵심어}`로 문서 전체에서 언급 위치를 한 번 훑는다. 다른 위원 질의 구간이나 결산검사 의견서 지적을 통째로 놓친 적이 있다.
- 2023년 이후 고양시의회 회의록 `text.txt`는 어절 사이가 NBSP(U+00A0)다. 공백을 정규화해서 찾는다. 본문이 두세 번 반복된 회의록은 첫 출현을 `locator`로 쓴다.
- 새 자료를 직접 받았으면 수집 칸 규칙대로 Storage에도 올린다.
- 같은 숫자가 자료마다 다르면 둘 다 올리고 어느 쪽이 공식 값인지 적는다. 승인된 금액과 "예상" 금액을 나눈다. 발언 속 어림수는 두고 계산을 같이 적는다.
- 부재 기록은 발췌의 `notFound`만 보고 쓰지 않는다. 그 축을 어디서 어떤 검색어로 찾았는지 직접 확인하고, 필요하면 한두 번 더 찾아본다(지역 언론 포함). 그래도 없을 때 쓴다.
- 다 쓰면 `npm run pipeline -- check-facts programs/{id}`. 문제가 나오면 고친다.

## 지키기

- 작업 파일(스크립트, JSON, 내려받은 파일)은 `.loop/runs/{run}/{사업}/` 아래에만 둔다. 스크래치패드나 `/tmp`에 쓰지 않는다. 같은 실행의 다른 일꾼과 그 폴더를 같이 써서 같은 이름의 파일이 서로 덮인다.
- Firestore에는 `npm run pipeline`으로만 쓴다. 코드, 스킬 파일, 다른 사업의 문서는 고치지 않는다(기관 공통 자료나 다른 사업에 붙은 자료가 이 사업에도 닿으면 그 자료의 `subjects`에 이 사업을 더하는 것만 된다).
- 사람 이름은 `○○○`로 가린다. 사업을 평가하지 사람을 평가하지 않는다.
