받는 것: 사업 경로, 할 일(`초안` 또는 `고침`), 고침이면 검증 기록 경로.

## 먼저 읽기

- `.claude/skills/write-report/SKILL.md`의 "리포트 초안"과 "걸려 넘어진 것".
- 양식 `src/features/reports/doc/FORMAT.md`.
- `npm run pipeline -- ls programs/{id}/facts`, `…/absences`, `…/reports`.

## 개요 (초안 전에)

본문을 쓰기 전에 `.loop/runs/{run}/{사업}/outline.md`를 짧게 만든다. 검증 high의 절반 넘게가 "있는 자료를 리포트가 안 씀"이었다.

1. **자료 대조표**: 이 사업 자료마다 한 줄, "어느 축에 썼나" 또는 "왜 안 썼나". 이 사업 `subjects`가 붙은 자료만 보지 말고, `materials` 전체에서 사업 이름·세부사업 코드로 찾은 기관 공통 자료(계약 목록, 세출현황, 행정사무감사 결과보고서·조치결과)도 넣는다. 그런 자료에는 `subjects`에 이 사업을 더한다(파이프라인 `put`, 다른 필드는 그대로).
2. **"없다"고 쓸 문장 목록**: "공개되지 않았다", "확인하지 못했다", "제출하지 않았다"처럼 쓸 문장마다 부재 기록 번호를 붙인다. 부재 기록이 없거나 대조표에 반대 자료가 있으면 그 문장을 쓰지 않는다.

축별 판단표까지 만들지는 않는다(지난 실행에서 비용만 두 배가 됐다).

## 초안

- 리포트의 숫자·판정은 모두 사실 원장에서 출발한다. 원장에 없는 것을 새로 주장하지 않는다. 꼭 필요한 사실이 빠졌으면 원장에 먼저 올리고(`write-report`의 사실 원장 규칙대로) 쓴다.
- 7개 축 상태와 근거 수준은 사실로 정한다. 종합 판정은 쓰지 않는다(규칙으로 계산된다). `## 종합 판정` 구역에는 `### 다음 판단 시점` 목록만 쓴다. 판정 문단을 쓰면 문장 규칙에 걸린다.
- 축 카드 제목(`####`)은 사이트 ‘핵심 내용’에 그대로 나온다. 제목만 읽어도 무엇이 문제인지 알게 쓴다.
- 작업 파일은 `.loop/runs/{run}/{사업}/report.md`. `npm run pipeline -- put programs/{id}/reports/{기준일} report.md --status draft`. 양식·문장 규칙 오류가 나오면 고쳐서 다시 `put`한다.
- 통과하면 `--status in-review`로 다시 쓴다.
- 사실 원장의 `locator`·`quote`에 있는 자료의 필드 이름(`bizEndYmd`, `ctrtRate` 같은 원값 이름)이나 코드 낱말을 본문에 옮기지 않는다. "지방재정365의 사업 종료일 원래 값", "계약정보에 적힌 낙찰률"처럼 뜻을 풀고, `20271231` 같은 원값은 `2027-12-31`로 쓴다. 차량 모델명(iX1)이나 단위(kWh) 같은 고유 표기는 그대로 둔다.
- 출처표의 기관 칸은 그 자료를 낸 기관이다. 계산한 값은 출처가 아니라 `**계산**` 사실로 쓰고, 기관 칸에 `glasses`를 적지 않는다.
- 양식에서 자주 걸린 것: 머리말 `footNote`는 필수다. 줄 머리의 날짜(`2026. 2. 23.`)는 번호 목록으로 읽히니 `2026\. 2. 23.`로 쓴다. 감사·점검 이력의 `**그 뒤**` 문단에는 출처를 붙이지 않는다. 회의 날짜와 안건 연도를 헷갈리지 않게 연·월을 풀어 쓴다("2025년도 동의안"을 심사한 2024년 10월 회의).

## 고침

- 고치기 전에 지금 판을 `.loop/runs/{run}/{사업}/report.before-{검증 기록 id}.md`로 저장한다. 재검증이 고친 곳을 이 파일과 비교해 찾는다.
- 검증 기록의 지적을 하나씩 원문으로 다시 확인한다. 지적이 틀렸으면 고치지 않고 근거를 적는다.
- 지적마다 **같은 종류의 실수가 리포트 다른 곳에 있는지** 찾아 함께 고친다. 같은 숫자·같은 사실 번호·같은 자료를 쓴 문장을 리포트 전체에서 `grep`한다. 한 곳만 고치고 같은 오독이 다른 줄에 남아 재검증이 한 번 더 돈 일이 두 사업에서 있었다.
- 지적 밖의 문장은 바꾸지 않는다. 고치다가 새로 틀린 곳을 찾으면 고치고 따로 적는다.
- 게시된 판을 고칠 때는 덮지 않고 `reports/{오늘}`에 새로 쓴다(`slug`는 그대로). 아니면 같은 기준일에 다시 쓴다.
- 끝나면 `--status in-review`.

## 지키기

- 작업 파일(스크립트, JSON, 내려받은 파일)은 `.loop/runs/{run}/{사업}/` 아래에만 둔다. 스크래치패드나 `/tmp`에 쓰지 않는다. 같은 실행의 다른 일꾼과 그 폴더를 같이 써서 같은 이름의 파일이 서로 덮인다.
- Firestore에는 `npm run pipeline`으로만 쓴다. 코드, 스킬 파일, 다른 사업의 문서는 고치지 않는다(자료의 `subjects`에 이 사업을 더하는 것만 된다). 게시는 오케스트레이터가 한다.
- 사람 이름은 `○○○`로 가리고, 사람이 아니라 사업을 평가한다.
