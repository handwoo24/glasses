# 리포트 검증

작성자와 다른 눈으로 본다. 작성 세션의 대화나 메모를 받지 않고, Firestore에 남은 리포트·사실·부재 기록·자료 원문만 본다. 리포트를 고치지 않는다. 고칠 것은 검증 기록으로 남기고, 고치는 일은 write-report 세션이 한다.

대상: 사이트 `/orgs/{기관코드}/programs`에서 단계가 `검증`인 사업.

## 순서

1. `npm run pipeline -- ls programs/{id}/reports` — 가장 늦은 기준일의 리포트(`status: in-review`)를 `get`.
2. `npm run pipeline -- check-facts programs/{id}` — 인용이 원문에 그대로 있는지, 자료 파일이 바뀌지 않았는지. 문제가 나오면 그대로 지적 사항이 된다.
3. 리포트의 숫자·날짜·인용마다 출처 칩이 가리키는 자료와 사실 원장을 맞춰 본다. 계산된 사실은 다시 계산한다.
4. 축 상태와 근거 수준이 사실로 뒷받침되는지 본다. "판단 불가"를 "개선 필요"로 올린 곳, 반대쪽 자료(기관의 설명)를 빠뜨린 곳을 찾는다.
5. 부재 기록이 주장하는 "공개 자료에서 찾지 못함"이 실제로 그 검색으로 안 나오는지 한두 건 직접 찾아본다.

지적의 `evidence`도 공식 공개 자료(write-report의 출처 범위)로만 쓴다. 언론 보도는 그 자체로 다시 사실 확인이 필요하므로 근거가 아니라 단서다. 보도에서 실마리를 얻으면 그 내용을 담은 공식 원문(보도자료, 회의록, 공개 문서)을 찾아 그것을 근거로 적는다. 공식 원문을 못 찾으면 '빠진 반론'이 아니라, 부재 기록에 "보도에만 있고 공식 자료에서 확인 못 함"을 남기라는 `low` 지적으로 쓴다.

## 검증 기록

`programs/{id}/reviews/{기준일}-{n}`에 `ReviewSchema`(src/pipeline/schemas.ts) 양식으로 쓴다.

- `report`: 검증한 리포트 기준일.
- `findings[].type`: 수치 불일치 · 출처 불일치 · 근거 없음 · 단정 표현 · 빠진 반론.
- `where`: 리포트 안 위치(‘축별 근거 > ④ 비용 > 사실 2’).
- `severity`: 독자가 틀린 사실을 믿게 되면 `high`. `high`가 하나라도 있으면 `verdict: fail`.
- 지적이 없거나 `medium`·`low`만이면 `pass`.

`pass`면 상황판 단계가 `게시 대기`, `fail`이면 `고침`이 된다. 게시(`published/{slug}`)는 사람이 리포트를 읽고 `--status published`로 바꾼 뒤 한다.

## 끝낼 때

판정, 지적 수(중요도별), 가장 중요한 지적 한두 개를 사용자에게 알린다. `fail`이면 다음은 새 세션에서 write-report로 고치기.
