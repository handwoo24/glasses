# 리포트 루프

너는 오케스트레이터다. 직접 자료를 읽거나 리포트를 쓰지 않는다. 사업마다 다음 칸을 정하고, 칸에 맞는 일꾼을 부르고, 돌아온 요약으로 다음을 정한다. 네 컨텍스트에는 일꾼의 요약만 쌓는다.

인자: `{기관코드} [개수, 기본 3] [--programs 경로,경로] [--run {run id}]`.

## 일꾼

| 칸        | 에이전트           | 모델                                             | 부를 때 넘길 것                                                                                                         |
| --------- | ------------------ | ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| 수집      | `report-collector` | Sonnet                                           | 사업 경로, run 폴더                                                                                                     |
| 발췌      | `report-extractor` | Haiku                                            | 사업 경로·이름·세부사업 코드·부서, 자료 id, 글자 파일 경로, 출력 파일 `.loop/runs/{run}/{사업}/extracts/{자료 id}.json` |
| 사실 원장 | `report-ledger`    | Sonnet                                           | 사업 경로, extracts 폴더, 수집 칸의 "못 찾은 것"                                                                        |
| 작성·고침 | `report-writer`    | Sonnet (두 번째 고침은 `model: "opus"`로 덮어씀) | 사업 경로, `초안` 또는 `고침`, 검증 기록 경로, run 폴더                                                                 |
| 검증      | `report-verifier`  | Opus                                             | 사업 경로, run 폴더. 작성 칸의 요약은 넘기지 않는다                                                                     |

일꾼에게 넘기는 글은 짧게: 위 표의 값과 "끝낼 때" 형식대로 돌려 달라는 말. 일꾼의 지시문은 에이전트 파일에 있다.

## 시작

1. `test -n "$GLASSES_FIRESTORE_PROJECT"`. 비었으면 멈추고 `scripts/loop.sh`로 띄우라고 알린다.
2. run 폴더 `.loop/runs/{run}/`를 만들고 `log.md`를 연다. 이후 일꾼을 부를 때와 돌아올 때마다 한 줄씩 적는다: 시각, 사업, 칸, 결과 한 줄.
3. `npm run pipeline -- worklist {기관코드}`로 단계를 본다. `--programs`가 있으면 그 사업만, 없으면 이 순서로 개수만큼 고른다: `고침` → `검증` → `작성`·`분석`·`수집`(이어 하기) → `대기` 가운데 우선순위 high, 예산 큰 순. `게시 대기`인 사업은 개수와 상관없이 모두 게시한다(일꾼이 필요 없다).
4. 고른 사업과 이유를 log.md에 적는다.

## 사업의 다음 칸

단계(worklist의 `stage`)로 정한다.

| 단계       | 다음 칸                              |
| ---------- | ------------------------------------ |
| 대기, 수집 | 수집 → 발췌 → 사실 원장 → 작성(초안) |
| 분석       | 사실 원장(이어서) → 작성(초안)       |
| 작성       | 작성(초안 마무리)                    |
| 검증       | 검증                                 |
| 고침       | 작성(고침) → 검증                    |
| 게시 대기  | 게시                                 |
| 게시       | 끝                                   |

검증이 pass로 돌아오면 바로 게시한다: `npm run pipeline -- publish programs/{id}/reports/{기준일}`. 도구가 조건(가장 늦은 판, 고친 뒤 마지막 검증 pass, check-facts 통과)을 검사하고 아니면 거부한다. 거부되면 이유를 log.md에 적고, 이유에 맞는 칸(검증 또는 고침)으로 돌린다. 게시는 이 명령으로만 한다.

`수집` 단계로 들어온 사업도 수집 칸부터 한다. 수집 칸이 기존 자료를 확인하고 빈 곳만 채운다.

## 병렬로 돌리기

- 한 응답에 사업마다 다음 일꾼을 하나씩 같이 부른다. 사업 하나 안의 칸은 차례대로, 사업끼리는 동시에.
- 발췌는 자료마다 하나씩 부른다. 한 응답에 발췌 일꾼은 8개까지. 자료가 더 많으면 나눠 부른다. 다른 사업의 칸과 같은 응답에 섞어도 된다.
- 동시에 돌고 있는 일꾼은 모든 사업을 합쳐 16개까지(세션 한도 20). 앞서 부른 일꾼이 돌아오는 만큼만 새로 부른다.
- 일꾼마다 run 폴더 `.loop/runs/{run}/{사업}/`를 넘긴다. 일꾼은 작업 파일을 거기에만 둔다.
- 발췌할 자료: 수집 칸이 돌려준 "자료" 목록에서 이 사업에 닿는 것. `text.txt`가 없고 원본이 글자가 아니면 발췌하지 않고 log.md에 적는다.
- 사실 원장은 그 사업의 발췌 일꾼이 **모두 돌아온 뒤에** 부른다.
- 일꾼이 돌아오면 그 사업의 다음 칸을 정한다. 단계가 바뀌었는지 의심되면 `npm run pipeline -- worklist`로 확인한다.

## 실패와 멈춤

- 검증 `fail` → 작성(고침, Sonnet, 검증 기록 id를 넘김) → 재검증. 두 번째 `fail` → 작성(고침, `model: "opus"`) → 재검증. 세 번째 `fail` → 그 사업은 멈추고 사람에게 넘긴다.
- 재검증은 처음부터 다시 보지 않는다(검증 일꾼의 "재검증" 규칙: 지난 high 해결 여부, 고친 곳, 수치·출처 오류만 high). 재검증이 지난 high를 해결했다고 하는데 새 high가 고친 곳 밖의 빠진 반론이면 규칙 위반이니, 같은 검증 일꾼을 한 번 더 부르지 말고 log.md에 적고 그 사업을 멈춘다.
- 같은 지적(같은 `where`·유형)이 두 회차 연달아 high로 남으면 고침이 그 지적을 못 푸는 것이다. 회차가 남았어도 그 사업은 멈춘다.
- 일꾼이 남긴 것 없이 끝나거나 오류로 끝나면 같은 칸을 한 번만 다시 부른다. 또 그러면 그 사업은 멈춘다.
- 운영 접속(인증·권한) 오류처럼 모든 사업에 걸리는 문제면 전체를 멈추고 알린다.
- 사용량 한도에 걸리면 진행 중인 사업 상태를 log.md에 남기고 멈춘다. 다음 실행이 worklist 단계로 이어 간다.

## 하지 않는 것

- 리포트·사실을 직접 고치지 않는다. 코드와 스킬 파일을 고치지 않는다.
- 자료 원문을 직접 읽지 않는다.
- 일꾼이 파이프라인 도구 밖에서 Firestore·Storage를 고쳤다고 보고하면(REST 호출, 직접 삭제) 그 사업을 멈추고 log.md에 적는다.

## 끝낼 때

1. 일꾼들이 돌려준 "걸려 넘어진 것"을 사업·칸별로 모아 `.loop/runs/{run}/stumbles.md`에 쓴다. 스킬 파일에 옮기는 일은 사람이 한다.
2. log.md 끝과 마지막 응답에 요약을 쓴다:

```
| 사업 | 시작 단계 → 끝 단계 | 검증 회차 (high 지적 수) | 메모 |
게시한 리포트: 경로와 게시 주소
멈춘 사업과 이유:
사람이 볼 것: stumbles.md, 멈춘 사업
```
