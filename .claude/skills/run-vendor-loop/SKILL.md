# 업체 루프

사업 루프(`run-loop`)와 같은 방식이다. 너는 오케스트레이터다. 직접 자료를 읽거나 리포트를 쓰지 않는다. 업체마다 다음 칸을 정하고, 칸에 맞는 일꾼을 부르고, 돌아온 요약으로 다음을 정한다. 네 컨텍스트에는 일꾼의 요약만 쌓는다.

인자: `[기관코드] [개수, 기본 3] [--vendors 경로,경로] [--run {run id}]`.

`run-loop`의 "병렬로 돌리기", "실패와 멈춤", "하지 않는 것"을 그대로 따른다. 아래는 다른 점만 적는다.

## 일꾼

| 칸        | 에이전트           | 모델                                             | 부를 때 넘길 것                                                                                                                  |
| --------- | ------------------ | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 목록화    | `vendor-lister`    | Sonnet                                           | 사업 경로, run 폴더                                                                                                              |
| 수집      | `vendor-collector` | Sonnet                                           | 업체 경로, run 폴더                                                                                                              |
| 발췌      | `report-extractor` | Haiku                                            | 업체 경로·업체 이름·계약명·계약번호, 자료 id, 글자 파일 경로, 출력 파일 `.loop/runs/{run}/{사업}/{번호}/extracts/{자료 id}.json` |
| 사실 원장 | `report-ledger`    | Sonnet                                           | 업체 경로, extracts 폴더, 수집 칸의 "못 찾은 것"                                                                                 |
| 작성·고침 | `vendor-writer`    | Sonnet (두 번째 고침은 `model: "opus"`로 덮어씀) | 업체 경로, `초안` 또는 `고침`, 검증 기록 경로, run 폴더                                                                          |
| 검증      | `report-verifier`  | Opus                                             | 업체 경로, run 폴더. 작성 칸의 요약은 넘기지 않는다                                                                              |

## 시작

1. `test -n "$GLASSES_FIRESTORE_PROJECT"`와 `test -n "$DATA_GO_KR_SERVICE_KEY"`. 비었으면 멈추고 `scripts/loop.sh --vendors`로 띄우라고 알린다.
2. run 폴더 `.loop/runs/{run}/`를 만들고 `log.md`를 연다. 일꾼을 부를 때와 돌아올 때마다 한 줄씩 적는다.
3. `npm run pipeline -- vendor-worklist [기관코드]`로 조사 목록을 본다.
   - `toList`(업체 목록화가 남은 게시 사업)가 있으면 먼저 사업마다 `vendor-lister`를 부른다. 개수에 세지 않는다. 돌아오면 `vendor-worklist`를 다시 본다.
   - `vendors`는 이미 루프가 고를 순서(고침 → 검증 → 이어 하기 → 게시 대기 → 대기, 같은 단계면 우선순위·금액)로 정렬돼 있다. `--vendors`가 있으면 그 업체만, 없으면 앞에서부터 개수만큼 고른다. `게시 대기`인 업체는 개수와 상관없이 모두 게시한다.
4. 고른 업체와 이유를 log.md에 적는다.

## 업체의 다음 칸

사업 루프의 단계표와 같다(대기·수집 → 수집 → 발췌 → 사실 원장 → 작성(초안), 분석 → 사실 원장(이어서) → 작성, 작성 → 작성(마무리), 검증 → 검증, 고침 → 작성(고침) → 검증, 게시 대기 → 게시).

검증이 pass면 바로 게시한다: `npm run pipeline -- publish {업체 경로}/reports/{기준일}`. 업체 리포트는 `publishedVendors/{주소}`로 게시된다. 조건을 도구가 검사하고, 거부되면 이유를 log.md에 적고 맞는 칸으로 돌린다.

## 더 지킬 것

- 나라장터 개발 계정은 하루 1,000건이다. 수집 칸이 돌려준 "나라장터 호출 수"를 log.md에 더해 적고, 800건을 넘으면 새 수집을 부르지 않고 이어 하기·검증·게시만 한다.
- 같은 업체가 여러 사업에 나오면(같은 번호), 업체 단위 조회(제재·기본정보·시 계약 전체)는 첫 업체의 수집 칸이 받은 자료를 다음 업체의 수집 칸에 자료 id로 넘긴다.

## 끝낼 때

1. 일꾼들이 돌려준 "걸려 넘어진 것"을 `.loop/runs/{run}/stumbles.md`에 모은다. `write-vendor-report`에 옮기는 일은 사람이 한다.
2. log.md 끝과 마지막 응답에 요약:

```
목록화한 사업: 경로 → 카드 n개 (뺀 업체 m개)
| 업체 | 시작 단계 → 끝 단계 | 검증 회차 (high 지적 수) | 메모 |
게시한 업체 리포트: 경로와 게시 주소
나라장터 호출: n건
멈춘 업체와 이유:
사람이 볼 것: stumbles.md, 멈춘 업체
```
